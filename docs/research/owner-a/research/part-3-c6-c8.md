## 2. Artifact formats (from fetched docs)

### memray (https://bloomberg.github.io/memray/run.html, stats.html, transform.html, flamegraph.html, summary.html, api.html)
- Capture: `memray run` writes `memray-<script>.<pid>.bin` (lz4 compressed by default, `--compress-on-exit` default on). Binary, parsed by memray itself; no documented schema on pages read. `--aggregate` produces smaller files with per-location stats, usable with most reporters but NOT with the stats reporter or temporary-allocation analysis; `FileFormat.ALL_ALLOCATIONS` is required for those (api.html). `--native` captures must be reported on the same machine as the capture (so our Lambda cannot re-render native-trace captures; CI must run the reporter).
- Therefore the practical rule: CI should run `memray stats --json` and `memray transform csv|gprof2dot` and upload those outputs, not just the `.bin`. Our Lambda would need memray installed to read `.bin` (not evaluated; memray is a native extension - UNVERIFIED for Lambda packaging).
- `memray stats <file> --json -o out.json`: JSON export of the stats; fields per page: total allocations, total bytes allocated, histogram of allocation sizes, allocation type breakdown (MALLOC, CALLOC, MMAP...), top-N allocating locations by size and by count (default 5, `-n`), and tracked-process metadata (JSON only). Page warns "new fields may be added to the JSON output over time". Exact JSON key names are UNVERIFIED (not shown on the page).
- `memray transform csv`: one row per call stack contributing to the high-water mark; columns `allocator`, `num_allocations`, `size` (bytes), `tid`, `thread_name`, `stack_trace` (frames `function;file;line`, `|`-separated, most recent first). Also `gprof2dot` JSON (node fields: filename, function, total %, self %, num_allocs) and `speedscope` (named only). Flags `--leaks`, `--temporary-allocations`, `--temporary-allocation-threshold N`.
- Flame graph: HTML, with `--leaks`, `--temporary-allocations`, `--temporal`. The page does not say machine-readable JSON is embedded in the HTML; do not plan to parse the HTML.
- Summary reporter: table columns Own memory, Total memory, Allocation count; also `--temporary-allocations`.

### tracemalloc (https://docs.python.org/3/library/tracemalloc.html)
- `Snapshot.dump(filename)` / `Snapshot.load(filename)`. The dump format is NOT documented (page never names pickle); treat as opaque, loadable only via `Snapshot.load` in Python. Parsing it in our Lambda means loading it with Python tracemalloc (which unpickles-or-equivalent: format undocumented) - a security risk for client-supplied files. Safer: ask CI to upload a text/JSON export produced from `Snapshot.statistics('lineno')` (fields `count`, `size`, `traceback`) and `compare_to()` (`count_diff`, `size_diff`, `count`, `size`, `traceback`). This export schema would be ours, not a standard.
- Snapshots exclude blocks allocated before tracing started; tracebacks limited to the configured frame count.

### cProfile / pstats (https://docs.python.org/3/library/pstats.html, https://docs.python.org/3/library/profile.html)
- `Profile.dump_stats(filename)` writes results; `pstats.Stats('run.prof')` loads them; multiple files can be combined. Page states: "The profile data format is specific to the Python version that created it. There is no compatibility guarantee between Python versions or between different profilers."
- Sort keys `ncalls`, `tottime`, `cumtime`. The `Stats.stats` dict layout `(cc, nc, tt, ct, callers)` and the use of `marshal` are from my general knowledge only: UNVERIFIED (not on fetched pages). Because the format is version-specific and I could not verify its serialization, recommend CI uploads `print_stats` text or a CI-generated JSON export, never raw `.prof` for our Lambda to unmarshal.
- No argument values are stored, so it cannot show repeated identical inputs (C8.1).

### Others
- py-spy (https://github.com/benfred/py-spy): `py-spy record` outputs SVG flame graph by default; `--format` supports speedscope or raw data. The page does not mention memory profiling, so py-spy gives CPU hot-spot context only, not C6 evidence.
- Scalene (https://github.com/plasma-umass/scalene): text, JSON (`--json`), HTML (`--html`) outputs; per-line memory (Python vs native share, net MB), "Copy (MB/s)" copy volume, experimental leak detector. JSON field names UNVERIFIED.
- functools `lru_cache` `cache_info()` -> `hits`, `misses`, `maxsize`, `currsize` (https://docs.python.org/3/library/functools.html); only exists if the client prints/uploads it.

## 3. Deviations from taxonomy

Source checked: arXiv abs page https://arxiv.org/abs/2604.04809 (Mehditabar, Rajput, Sharma; "Watts This Smell", v2 8 Jul 2026) and https://arxiv.org/html/2604.04809 (first 100,000 of 111,210 characters read; final 11,210 not read).
- SRC-01 defines 12 primary smells (C1..C12) and 65 root causes; it mapped 55 of 65 to code in a Python dataset. C6 = "Unnecessary Memory Usage", C8 = "Missing Reuse"; the sub-names (Unnecessary Object C6.S1 ... Missing Local Lookup Caching C8.S3) match the taxonomy.
- NOT observed in the Python dataset: C6.6 Leaked Resource Handles ("absence of persistent connections in the dataset"), C6.7 Leaking Mutable Defaults ("absence of multi-call objects in the dataset"), C8.4 Redundant Data Fetching. The taxonomy keeps them as Python-detectable checks with SRC-01 as sole source, but SRC-01 gives no Python evidence for them. They are taxonomy extensions, to be justified by the tool docs above, not by SRC-01.
- SRC-01 is a code-pair energy study (profiled Python pairs for energy/time/memory, LLM-classified). It contains no detection rules, no tool names, and no artifact formats. All "detection signal" cells (memray/tracemalloc, cProfile counts, X-Ray) are taxonomy author choices, not from SRC-01.
- Per the HTML summary: C6 category median energy saving 3,670 J (C5 3,989 J); no median reported for C8; no per-root-cause savings. So claims like "tiny gain" (C8.3) or "gain varies" (C8.2) are NOT supported by SRC-01; C8.2's re-cache statement is supported by Python `re` docs instead. The abstract says "memory-related smells yield the highest per-fix energy savings".
- C6.6 resource column says "Memory, GC/CPU, energy": handles are file descriptors, not heap; no fetched profiler page tracks them.
- C6.7: taxonomy says signal "Memory profiler; AST". AST is sufficient (B006/W0102/CodeQL); memory profiler is not needed.
- C8.1-C8.3 rows say detection "Tracing repeated calls / Profiler call counts" and resource "CPU, I/O": cProfile call counts cannot show repeated-argument calls (C8.1) nor attribute lookups (C8.3); "I/O" resource applies only to C8.4.
- C8.1 "Validate hit rate first" cannot be done from the artifacts the taxonomy names.
- All taxonomy rows are Verify=Unverified and "needs discussion OQ-1"; this research does not resolve OQ-1 (I had no access to what OQ-1 is beyond the label).
